# Edge Lab

A **virtual-coin** game platform where players compete against other players and bots, and the
app grades each decision using probability and expected value.
**No real money is involved. Coins have no monetary value.**

> Status: Phase 7 (bankroll simulator and calibration game). Polish and the final write-up come in the last phase.

## Key design rule

Coins are integers. Every wallet change is written to an append-only ledger in the same
database transaction, and the balance update is a single conditional `UPDATE`, so a wallet
can never go negative and its balance can always be re-derived from its history.

## Probability engine (Phase 3)

Pure Python, no third-party packages. Every exact answer is a `fractions.Fraction`, so there is no rounding.

| Module | What it does |
|---|---|
| `exact.py` | Dice-sum distribution by **dynamic programming**; all ten 5-card poker hand counts by **combinatorial counting**; hypergeometric pmf/cdf; birthday problem |
| `poker.py` | 5-card hand classifier (handles the A-2-3-4-5 "wheel") |
| `montecarlo.py` | Seeded simulation, **partial Fisher-Yates** shuffling, **Wilson 95% confidence intervals**, log-spaced sample sizes |
| `convergence.py` | Many replicates of the whole experiment: error vs n, fitted log-log slope, 95%-interval **coverage** |
| `chart.py` | Dependency-free SVG log-log chart with the 1/sqrt(n) reference line |

### How it is verified

- Poker counts (4, 36, 624, 3,744, 5,108, 10,200, 54,912, 123,552, 1,098,240, 1,302,540) sum to C(52,5) = 2,598,960, and a test **enumerates every one of the 2,598,960 hands** with the classifier and checks the formulas agree.
- Dice, hypergeometric and birthday results are checked against known values (e.g. 23 people give 50.73%) and against each other (hypergeometric "5 cards of one suit" vs the poker flush counts).
- Monte Carlo estimates must land within 4 standard errors of the exact value, are reproducible from their seed, and do not depend on Python's global random state.
- Tests were **mutation-checked**: deliberately breaking the flush formula, the Wilson z-value, the birthday product and the shuffle each made a test fail.

### Convergence results

The standard error of an estimate is sqrt(p(1-p)/n), so error should fall like 1/sqrt(n): a straight line of slope **-0.5** on a log-log chart. Quadrupling the trials only halves the error. Measured with 200 replicates (100 for poker), seed 2026:

| Event | Exact p | Fitted slope | 95% interval coverage |
|---|---|---|---|
| Two dice sum to 7 | 0.16667 | -0.483 | 95.1% |
| Birthday match among 23 people | 0.50730 | -0.498 | 95.0% |
| Exactly 2 aces in a 5-card hand | 0.03993 | -0.492 | 96.2% |
| One pair in 5-card poker | 0.42257 | -0.510 | 94.2% |

Coverage close to 95% means the Wilson intervals are honest: they contain the exact answer about 95% of the time.

![Birthday problem convergence](docs/charts/birthday_match_among_23_people.svg)

Regenerate the charts and tables:

```bash
cd backend
python -m app.probability.report --out ../docs/charts
```

### Limitation

Rare events (a royal flush is 1 in 649,740) need far more trials before the estimate is useful, because the *relative* error shrinks slowly. Variance-reduction methods such as importance sampling are not implemented yet.

## Game engine, bots and tournaments (Phase 4)

Pure Python, no web or database code. Virtual coins only.

**Dice Duel.** Both players ante 10 and secretly roll one die. The first player (the button alternates each hand) checks, or bets any whole number of coins up to the smaller stack. Facing a bet, the other player calls or folds. Higher die takes the pot; a tie returns everyone's chips.

**Kuhn poker.** A 3-card deck (J < Q < K), one ante each, one fixed bet size. Check/bet, then call/fold (a check can be answered with a bet). It was solved in 1950: with optimal play the first player loses exactly **1/18** of an ante per hand.

| Bot | Behaviour |
|---|---|
| `random` | uniformly random legal action |
| `cautious` | bets small (5% of its stack) and calls only with a strong hand (win chance of about 2/3 or more) |
| `ev` | risk-neutral: maximises expected chips assuming the opponent always calls, so it bets everything on any positive edge |
| `kelly` | maximises expected **log** wealth. The closed form is to risk the fraction f* = (w - l)/(w + l) of its bankroll; the bot uses half of that |

**Fair-play rules enforced by design.** A bot only receives a `Decision`: its own win/tie/lose odds, stacks, pot and legal bet range, never the opponent's hidden value. `Hand.public_state()` is safe to show both players. Live games should use `secure_rng()` (OS entropy); simulations use a seeded generator so any result can be replayed.

```bash
cd backend
python -m app.games.tournament --game dice --matches 300 --mirror    # or --game kuhn
```

### How it is verified

- **Kuhn's published value.** Running the known equilibrium strategies through this engine gives exactly -1/18 for the first player (for three different equilibria), and a 60,000-hand simulation agrees.
- **Every line of play.** Tests walk the full game tree for small stacks and check each outcome is zero-sum, no player loses more than their stack, and the number of lines matches a hand count.
- **Hidden information.** Two hands that differ only in the opponent's hidden value must look *identical* to the other player (same `Decision`, same `public_state`).
- **Kelly** is checked against a brute-force search of expected log wealth over every integer bet size.
- **Exact analysis.** `exact_hand_ev` enumerates every deal for the deterministic bots. The simulated tournament must agree with it (it does: Kuhn cautious vs ev is exactly +1/6 chip per hand, and the simulated 95% interval contains it).
- **Mutation-checked.** Eight deliberate bugs (reversed winner, chips created on a fold, a hidden-information leak, a broken Kelly formula, ...) were each caught by the tests.

### What the results do and do not show

- **The "EV-maximising" bot is not the strongest.** It maximises expected value under a simple model (opponent always calls, hidden value uniformly random). When that model is wrong it loses, and it also goes all-in so often that matches end in a handful of hands. Kelly beats it in about 98% of Dice Duel matches because it sizes bets to its edge instead of risking everything.
- **Why cautious beats Kelly (about 7 matches in 10).** Kelly's model ignores what the opponent's *call* reveals. The cautious bot only calls with a 5 or 6, so whenever a Kelly bet is called, the caller holds a 5 or a 6:

  | Kelly holds | edge in Kelly's model | edge given that cautious called |
  |---|---|---|
  | 4 | +0.167 | -1.000 |
  | 5 | +0.500 | -0.500 |
  | 6 | +0.833 | +0.500 |

  This is *adverse selection*: the counterparty chooses to trade only when it is good for them. It is closely related to the effect that makes a market maker's quotes lose money to better-informed traders.
- **In Kuhn poker Kelly and EV play identically** (`kelly vs ev` is +0.00 per hand, and they beat the random bot by the same margin), because there is only one bet size to choose.
- **Cautious beats the naive bots in Kuhn (96% to 99% of matches) for the same reason:** `ev` and `kelly` call with a Queen against a bet that, from a cautious player, only ever comes from a King.

### Limitations

- None of the bots reads what the opponent's actions reveal, so none bluffs or detects bluffs. They are baselines, not strong players.
- Results depend on these exact rules and bot definitions (for example, a different bet limit changes the ranking). They are not general claims about "Kelly" or "EV" strategies.
- Both games have a single betting round with no raises.
- Match results depend on the stopping rule (200 hands or bust); with all-in play most Dice Duel matches are decided within a few dozen hands.

## Live tables (Phase 5)

Two players (or a player and a bot) sit at a table, play a match over a WebSocket, and the server settles both wallets in **one atomic step**. All coins are virtual.

### How money moves

1. **Create a table** (`POST /tables`): nothing is charged yet.
2. **The match starts** when the second player connects (or immediately for a bot table). Both **buy-ins are escrowed** all-or-nothing: if either player cannot cover it, neither is charged.
3. **Bets come from the table stack**, not the wallet. The rest of your wallet is untouched.
4. **The match ends** (max hands, someone busts, someone leaves, a timeout or disconnect). Both wallets are paid their final stacks in a single database transaction.
5. **Safety checks:** payouts must equal the escrow and go only to the players who escrowed, and a match can be settled **once**. If settlement keeps failing, the escrow stays put and is **refunded on the next server start**.

### What happens when things go wrong

| Situation | Behaviour |
|---|---|
| Illegal or out-of-turn move | `error` message (`illegal_action`, `not_your_turn`); nothing changes; the turn stays with the right player |
| Malformed JSON, unknown message, bad amount, oversized message | `error` message; after 5 refused messages in total the client is disconnected |
| No move within 30 s | automatic action: fold if facing a bet, otherwise check. 3 timeouts in a row ends the match |
| Player disconnects while the other human waits | their turns are played automatically (fold/check) so nobody is stuck |
| Disconnect longer than 30 s | match abandoned: they lose the chips in the current hand and keep the rest of their stack |
| Reconnect inside the grace period | same user reconnects and resumes; the old socket is closed |
| `leave` message | match ends the same way as an abandonment |
| Both players gone | no runaway auto-play; the match is abandoned after the grace period |

The turn clock is **absolute**: it keeps running while a player is disconnected, so dropping and reconnecting cannot buy extra time.

### Protocol

Connect to `ws://host/ws/tables/{table_id}` with your login cookie. Messages are JSON.

| Client sends | |
|---|---|
| `{"type":"action","action":"check"}` | also `"call"`, `"fold"` |
| `{"type":"action","action":"bet","amount":50}` | whole number, within `min_bet`..`max_bet` |
| `{"type":"leave"}` / `{"type":"ping"}` | |

| Server sends | |
|---|---|
| `waiting` | you are the host; waiting for an opponent |
| `state` | your view: `you` (seat), `your_value` (your OWN die/card), public `hand`, `decision` (your legal actions, only on your turn), `deadline_s`, `opponent` |
| `hand_result` | chip changes; the hidden values are revealed **only if there was a showdown** |
| `auto_action`, `event` | the table acted for someone / an opponent connected or disconnected |
| `match_over` | reason, final stacks, your payout and new balance |
| `error` | `code` and `message` |

REST: `GET /tables` (open tables), `POST /tables` (`{"game":"dice","buy_in":500,"bot":"kelly"}`), `GET /tables/mine`. Games: `dice` (buy-in 100 to 1,000) and `kuhn` (10 to 100). Bots are real accounts named `bot_random`, `bot_cautious`, `bot_ev`, `bot_kelly`; humans cannot register those names.

### Fairness and security

- **Hidden information.** A player is only ever sent their own value. Tests check that two hands differing only in the opponent's value produce identical views, that no message carries a private field, and that a fold never reveals cards.
- **WebSocket hardening.** Login cookie required, handshake refused for foreign `Origin`s (cross-site WebSocket hijacking), messages capped at 2 KB, strict parsing, strike limit.
- **One table per user**, reserved before any `await` so it cannot be raced.
- Live games use `secrets`-grade randomness; tests inject seeded generators.

### How it is verified

The table logic is pure Python (standard library + `asyncio`), so it is tested with **simulated clients and an in-memory ledger**: over 100 test cases covering escrow and settlement, privacy, illegal moves, timeouts, every disconnect case, settlement failure and recovery, simultaneous joins, and a randomised 40-round property test (at least 25 rounds are played; poor players are skipped) that checks **no coin is ever created or destroyed** and every match nets to zero in the transaction log. The timing-sensitive tests were run repeatedly, including under CPU load. Seventeen deliberate bugs (settling the wrong amount, paying twice, non-atomic escrow, leaking a card, letting a player reset their clock, ...) were each caught by the tests.

The in-memory ledger and the SQL ledger are held to **one shared contract test-suite**, so the database version must behave exactly like the verified one.

### Limitations

- **Single server process.** Tables live in memory, and startup refunds every unfinished match, which is only correct if no other process owns tables.
- No game UI yet (Phase 9), and hands are not yet stored for grading (Phase 6).
- Bots are real wallets: a bot that loses everything cannot start a match (`bot_unavailable`).
- No per-IP rate limiting on connections.

## Decision grading and leaderboards (Phase 6)

After every match, each decision a human made is graded and stored.

**EV of a decision** = the average chips you win or lose in that hand if you take that action and play the best you can afterwards. It is computed *exactly*, by enumerating every hidden value the opponent might hold, weighted by how likely the reference opponent was to have acted the way this opponent did (a bet from a player who only bets strong hands is evidence of a strong hand). **Regret** = EV of the best action minus EV of the action taken: never negative, and zero when you chose a best action.

Everyone is graded against the same **fixed reference opponent**, so grades are comparable between players:

- **Dice Duel:** the EV bot from Phase 4.
- **Kuhn poker:** the published Nash equilibrium.

Example (Dice Duel, ante 10, you hold a 4):

| Action | EV | |
|---|---|---|
| Bet 1 | +1.83 | best: everyone calls a bet that small, so you collect a little extra |
| Check | +1.67 | regret 0.17 |
| Bet 49 | -6.50 | only hands that beat you call; the rest fold |
| Bet 990 | -328.33 | regret 330.17 |

### The two leaderboards

| Board | Ranked by | Contains |
|---|---|---|
| **Skill** | cumulative EV earned (ties broken by lower regret) | no luck of *outcomes*; shows deal value, regret per decision, luck |
| **Coins** | net coins won in finished matches | luck + skill |

Each row also shows the player's rank on the other board, and the skill board shows `luck = actual coins - EV earned`. Bots are on neither board. `skill-vs-luck.html` explains all of this with a worked example, and a test checks that every number quoted on it comes from the grader.

### An honest limitation: EV still contains the luck of the deal

Removing the luck of *outcomes* does not remove the luck of *which cards you were dealt*. Even **perfect play earns -8.33 coins from an opening roll of 1 and +338.33 from a roll of 6** (1,000 buy-in). At a 100-coin buy-in the per-hand range is -8.3 to +38.3, so over 35 hands the deal alone moves a player's total EV by roughly +/-93 coins. In my simulation of a skilled and a timid player over about 35 hands each, their EV totals were within 15 coins of each other (-122.5 and -136.7) even though their regret differed by about 300 (0 against 306). The deal had swamped the skill difference in EV.

So each player's EV splits into two parts, and the board shows both:

> **EV earned = deal value - regret**

*Deal value* (what perfect play would earn from your cards) is luck; *regret* (what your mistakes cost) is skill, and is exactly zero for a player who always picks a best action, whatever they hold. The board is ranked by EV earned as specified, but **regret per decision is the cleaner measure of skill**, especially over few hands.

### What is counted

- Only decisions the player made. Automatic moves (timeouts, disconnects) are not graded, and a hand containing one does not count towards EV.
- A hand contributes the EV of the player's **last** decision in it, so nothing is counted twice. Regret is summed over every decision.
- A hand in which a player never had a decision (the opponent checked and the hand went to showdown) counts in neither EV nor actual coins, so luck compares like with like.
- A match that failed to settle is refunded and therefore **not** graded. A grading failure can never affect anyone's coins.

### API

| Method | Path | Purpose |
|---|---|---|
| GET | `/me/decisions?limit=50&offset=0` | your graded decisions, newest first |
| GET | `/leaderboards?min_hands=1&limit=50` | `{"skill": [...], "coins": [...]}` |

### How it is verified

- **Nash equilibrium as ground truth.** At equilibrium every action a player mixes over must have *exactly zero regret*, and the best-response values must be exactly -1/18 for the first player and +1/18 for the second. A test checks all 12 information sets, so a wrong evaluator or a wrong reference table fails immediately.
- **Independent formulas.** Dice Duel EVs are recomputed by hand-written formulas (never touching the engine) for every roll, bet size and response.
- **Exhaustive shortlist check.** The grader evaluates a handful of bet sizes at the opponent's break points; a test proves that finds the true optimum for **every one of the 5,940 (roll, stack) combinations**.
- **End to end.** Simulated skilled, reckless and timid players play real tables: the skilled player (who always plays the grader's best action) has regret of exactly zero, the others have hundreds.
- **Stores.** `MemoryGradeStore` and `SqlGradeStore` share one contract test-suite, as the ledgers do.
- **Mutation-checked.** 19 deliberate bugs (an evaluator that ignores what bets reveal, one that peeks at the opponent's cards, a wrong Nash table, double-counted hands, grading automatic moves, reversed rankings, ...) were tried; 17 were caught, and the other two are provably equivalent changes that cannot alter behaviour.

### Limitations

- The reference opponent is a **model**, not the truth. A call the grader marks as a mistake might be good against a particular real opponent who bluffs a lot. The board measures closeness to the best play against a fixed standard, so it cannot reward a read on one player.
- Small samples are noisy: look at the number of hands.
- Only the two games above, with one betting round.
- As in Phase 5, the database store and the web layer are covered by tests that need your normal test environment.

## Bankroll simulator and calibration game (Phase 7)

### Bankroll simulator

One bet, repeated: it wins with probability `win` (paying `odds` x your stake), loses with probability `lose` (costing your stake), and otherwise pushes (like a tie in Dice Duel). Staking a fraction `f` of your bankroll each time, the long-run growth per bet is

> g(f) = win x ln(1 + odds x f) + lose x ln(1 - f)

The **Kelly fraction** maximises it: `f* = (odds x win - lose) / (odds x (win + lose))`. With no pushes this is the textbook `(bp - q)/b`, and for Dice Duel it equals the `(w - l)/(w + l)` the Phase 4 Kelly bot uses. Beyond about **twice** Kelly growth turns negative even though every bet is favourable.

You can stake a multiple of Kelly, a fixed percentage of the bankroll, or a flat number of coins, and optionally set a profit goal. The simulator reports the **risk of ruin** (the bankroll ever touching a level you choose, with a Wilson 95% interval), the distribution of final bankrolls, drawdowns, and the measured growth rate next to the formula's prediction.

55% to win at even money, 200 bets, 2,000 paths, seed 1, ruin = falling to 10% of the start:

| Strategy | Stake | Median final | Mean final | Risk of ruin | Typical worst drawdown | Growth per bet (formula) |
|---|---|---|---|---|---|---|
| Half Kelly | 5% | 2,118 | 2,712 | 0.0% | 42% | +0.0037 (+0.0038) |
| Full Kelly | 10% | 2,723 | 7,517 | 2.6% | 70% | +0.0049 (+0.0050) |
| 2x Kelly | 20% | 973 | 58,832 | 42.1% | 96% | -0.0003 (-0.0001) |
| 3x Kelly | 30% | 39 | 274,018 | 79.8% | 100% | -0.0165 (-0.0162) |

Look at the last rows: at 3x Kelly the *average* bankroll is enormous while the *typical* one (the median) has collapsed, because a few very lucky paths drag the mean up. That is why the page shows both, and three charts: where the paths ended (histogram), how they fan out over time, and the Kelly growth curve.

**How it is verified** (against exact answers, not just against itself):
- The gambler's-ruin formula is checked against an independent Markov-chain solver, and the simulator against the formula for three win probabilities (including a fair game).
- Every statistic (risk of ruin, chance of finishing below the start, mean final bankroll) is compared with a **full enumeration of every possible win/lose/push sequence** for short runs.
- Kelly's fraction is checked by brute force: the best of 100,000 candidate fractions is the Kelly fraction. The measured growth rate matches the formula at five different stake sizes.
- Dice Duel presets equal the odds the real game engine reports.
- 12 deliberately injected bugs were tried (a win that pays the stake instead of stake x odds, a push counted as a loss, drawdown measured from the wrong point, collapsed percentile bands, ...); all are caught. One of them initially slipped through, which exposed a weak test that has since been fixed.

**Limits:** it assumes the odds are known and every bet is independent. Kelly is very sensitive to the *estimate* of your edge: overestimating it is the same as staking a multiple of Kelly, which the table shows is dangerous. Bankrolls are in fractional coins, work per request is capped, and at most two simulations run at once.

### Calibration game

You are asked a probability question (dice, poker hands, the birthday problem, drawing cards, Dice Duel, runs of heads). You give a probability; **only then** does the server actually run the random experiment (rolling, dealing, flipping with secure randomness) and tell you whether the event happened. Questions come from this project's own exact probabilities, so the true answer is always known.

You are scored with the **Brier score**, `(forecast - outcome)^2` where the outcome is 1 or 0 (lower is better; always saying 50% scores exactly 0.25). One experiment is luck, so the game also reports numbers that use the exactly known probability `p`:

| | Formula | Meaning |
|---|---|---|
| Expected Brier | `p(1-f)^2 + (1-p)f^2` | the score you would average over many repeats |
| Uncertainty | `p(1-p)` | the expected score of someone who *knows* `p`; nobody can beat it |
| Excess (reliability) | `(f-p)^2` | what your estimate cost beyond that unavoidable noise |

and `expected Brier = uncertainty + excess` exactly. The summary shows your scores over time, a calibration (reliability) chart, and your average error for each kind of question, so you can see, for example, that you overestimate poker hands.

Rules that keep it honest: you keep your question until you answer it (no rerolling to dodge hard ones), each question is answered once, and the outcome is generated after the forecast is locked in and cannot depend on it.

**How it is verified:**
- Every question's exact answer is checked by **brute force**: all dice rolls, all coin sequences up to 12 flips for every run length, an independent hypergeometric formula, the birthday product, and the poker hand counts.
- Each experiment is run thousands of times and must happen as often as its exact probability says.
- A simulated player who always states the true probability has exactly zero excess and scores the uncertainty floor; "always 50%" scores exactly 0.25 every time; biased and overconfident players are detected with the right sign. The proper-scoring-rule property (honesty is optimal) is checked numerically.
- 12 deliberately injected faults in the pages (a script reading a field the API does not return, a wrong number in the text, ...) and 12 in the scoring and question code were all caught.

## Security notes

- Passwords are hashed with **Argon2id** (random salt per password). Plain passwords are never stored or logged.
- Passwords must be 8 to 128 characters. Usernames are 3 to 32 letters, numbers or `_`, and are stored **lowercase**, so `Alice` and `alice` are the same account.
- Sessions are random 256-bit tokens in an `HttpOnly`, `SameSite=Lax` cookie. The database stores only a SHA-256 hash of the token, so logout truly revokes it and a leaked database cannot be used to hijack sessions.
- Login failures give the same message for "unknown user" and "wrong password", and unknown users still cost one hash check, to limit username probing.
- Set `COOKIE_SECURE=1` when serving over HTTPS. It is off by default because browsers do not send `Secure` cookies over plain `http` during local development.

## Known limitations (planned for later)

- No login rate limiting or account lockout yet, so password guessing is not throttled.
- CSRF protection relies on `SameSite=Lax` cookies and POST-only state changes; there is no CSRF token.
- No password reset or change-password flow.
